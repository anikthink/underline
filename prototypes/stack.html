Stack and first version

How Nightstand gets built: Tauri, what goes into version 1, and what to try first because it might not work.

Decided 29 Oct
Tauri 2, Mac first. The interface is built in the web view, with the same HTML and CSS as the prototypes. Books are rendered with foliate-js. A Rust core handles the library folder, the database, Open Library and the devices.
Why, in one line
The reader has to be a web view whichever way you go, so a SwiftUI app would be a native shell around web content anyway.
Biggest risk
Making AZW3 files for the Kindle without calibre. Try it first, before anything else is built.

Why Tauri

  1. Books are web content either way. Apple has no EPUB renderer for Mac apps, and Readium's Swift toolkit, the main native option, targets iOS. Its macOS builds currently fail. A SwiftUI Nightstand would show books in a WKWebView running a JavaScript renderer. Tauri uses the same WKWebView on the Mac, so the reader would look and perform the same either way.
  2. The prototypes carry over. The library, Notes, ⌘K, Settings and the device pages are already HTML and CSS with real behaviour. In Tauri they become the app with their data swapped for real calls. In SwiftUI every screen is rebuilt from scratch.
  3. Windows and Linux stay possible. Nothing in the design is Mac-only. The same Tauri code builds for Windows (WebView2) and Linux (WebKitGTK). Calibre's users are on all three, and they're the most likely early users.
  4. Rust is a good fit for the core. SQLite, file watching, unzipping EPUBs, reading the Kobo's database and spotting a device being plugged in are all well covered by mature crates.

When SwiftUI would win

If Nightstand is only ever a Mac app and feeling native matters more than anything else, choose SwiftUI. Spotlight indexing of underlines, Quick Look previews of books and system-wide Services are much easier natively. Even then, the reader would still be a web view running foliate-js, so the next section's risks stay the same.

Try these first

1. EPUB to AZW3 without calibre

Kindles don't show EPUB files copied over USB, so most sends need converting. Amazon's KindleGen is discontinued. Calibre's converter is GPL and around 200 MB. The one small route found is the Go library leotaku/mobi, used by the MIT-licensed kindle-cli, which writes KF8 (AZW3) directly. It could run as a small helper program bundled with the app.

Test: convert all 16 library books, copy them to a real Paperwhite and check covers, the table of contents, images and Kindle's own highlights. If it fails, use calibre when it's installed, and otherwise send only books that already have an AZW3, MOBI or PDF.

Result, 30 Oct: works on a computer. Four Gutenberg books convert in 0.1–3 seconds, and KindleUnpack and foliate-js both read them back with all text, images, covers and contents. The library needed a small patch to its contents index. Links inside a book become plain text, and the contents list is flat. Still to check on a real Paperwhite. Details in spikes/azw3/README.md.

2. Keeping underlines on the right words

Underlines are stored as EPUB CFIs, the standard way to point at a place in a book, which foliate-js supports. Kindle clippings only give a location number, so passages brought back from the Kindle are found by searching the book's text, which is how the Devices prototype describes it.

Test: underline in Middlemarch, edit the book's details (which rewrites the file), and check the underlines are still on the same words. Bring in a real My Clippings.txt and count the matches.

Result, 30 Oct: works, with one change: each underline is stored as a CFI and its quote with the words either side. After Edit details, all 300 test underlines in Middlemarch stayed on their words by CFI alone. After a harsher rewrite, like a corrected re-download, CFIs found none, and 10 pointed at the wrong words without failing; the quote put all 300 back. A generated My Clippings.txt from the converted books matched 250 of 250 highlights once the words around each one were read from the AZW3 itself; by location alone, 7 short ones landed on another copy of the same phrase. A real My Clippings.txt is still to check. Details in spikes/anchors/README.md.

3. The pages layout on a long book

Middlemarch is about 320,000 words. Paginating chapter by chapter in a web view is normal practice, but page numbers that stay stable across font sizes, like "p. 317 of 810", need a fixed reference rather than counting screens.

Test: open Middlemarch, then change the size from 15 to 24 pt and back. Turning a page should feel instant, and the page number should stay put.

Result, 13 Nov: works in WebKit, the engine Tauri uses. A page is 2,000 characters of text, so Middlemarch has 905 pages, and the number never changes with font size. Turns take about 5 ms and a size change under 60 ms. The Reader has to remember the word being read and return to it after a size change; without that, 5 of 9 changes lost your place. Books stored as one huge file take 8.7 s to open in WebKit, so Nightstand should split them when they are added. Details in spikes/pages/README.md.

4. Kobo's database

Highlights and reading positions are read from .kobo/KoboReader.sqlite, which isn't documented and changes with Kobo's firmware. Nightstand only reads it, never writes, which keeps the risk small.

Test: read a Clara 2E and a Libra Colour on current firmware.

Version 1

In

  • A library in one folder, grouped by status, with shelves and keyboard control
  • Adding books by dropping files, copied in, with Open Library lookups
  • Editing details for one book or many
  • The Reader for EPUB, MOBI and AZW3: pages and scroll, themes, fonts, underlines with the four fixed labels, notes
  • Notes with Revisit, and Markdown export (off until a folder is chosen)
  • ⌘K, with text search in the open book only, and the G shortcuts
  • Settings
  • Kindle and Kobo over USB: send, and bring back highlights and Kobo progress automatically
  • Import from calibre
  • macOS only

Not yet

  • Reading PDFs inside Nightstand. They open in Preview until then
  • Text search across every book
  • Send to Kindle by email, and Kobo over Wi-Fi
  • Sync between computers, or any account
  • Windows and Linux builds
  • Renaming labels
  • Books with DRM. They're listed on devices but never opened or copied

Order of work

  1. Tests 1 and 2 above. Neither needs the app. If AZW3 conversion fails, the Devices design changes before anything is built on it.
  2. Library and Reader. The folder, the database, adding books, the library list and the Reader with underlines. This is the app someone could use daily.
  3. Notes, ⌘K and Settings. Mostly the prototypes' code, wired to the database.
  4. Devices and calibre import. Sending, bringing things back and the queue for unplugged devices.
  5. Signing and release. A notarised Mac download, and auto-update through Tauri's updater.

Sources

  • Readium mobile toolkits, plus the flutter_readium docs and Swift Package Index build results on the Swift toolkit's macOS status
  • foliate-js: EPUB, MOBI, KF8 (AZW3), FB2 and CBZ in the browser. The author calls the API unstable, so pin a version
  • kindle-cli, which writes AZW3 using github.com/leotaku/mobi
  • Kindle and sideloaded EPUB and a MobileRead thread on sideloading. These are community sources; Amazon doesn't publish a USB format list
